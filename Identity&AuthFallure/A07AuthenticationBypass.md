# Звіт з виконання завдання: A07 Authentication Bypass (WebGoat)

## 1. Мета завдання
Дослідити вразливості логіки аутентифікації у вебзастосунках на прикладі обходу механізму перевірки контрольних питань (2FA / Security Questions). Опанувати практичні навички використання Burp Suite для перехоплення, аналізу та модифікації HTTP-запитів з метою експлуатації логічних помилок на серверній стороні (Backend).

## 2. Теоретичні відомості
**Authentication Bypass (Обхід аутентифікації)** — це клас вразливостей, який дозволяє зловмиснику отримати доступ до системи або підвищити привілеї, оминаючи передбачені механізми перевірки особи. У контексті OWASP Top 10 (A07:2021-Identification and Authentication Failures), такі проблеми часто виникають через:
*   Неправильну реалізацію логіки перевірки на бекенді (наприклад, алгоритм пропускає користувача, якщо параметр валідації взагалі відсутній).
*   Довіру до даних, що надходять від клієнта (Client-side trust).
*   Відсутність підходу **"Default Deny"** (заборонити за замовчуванням) під час написання умов перевірки.

## 3. Хід виконання (Практична частина)
Для початку роботи я розгорнула локальний сервер WebGoat у Docker-контейнері. У команді було налаштовано прокидання портів (8080 та 9090) на локальний інтерфейс 127.0.0.1, а також вказано часовий пояс для коректної генерації токенів:
```bash
sudo docker run -p 127.0.0.1:8080:8080 -p 127.0.0.1:9090:9090 -e TZ=Europe/Amsterdam webgoat/webgoat
```

### Аналіз функціоналу
У завданні пропонується форма верифікації облікового запису, яка вимагає відповісти на два контрольні питання (secQuestion0 та secQuestion1), задані під час реєстрації.


Для дослідження механізму валідації я використала проксі-сервер **Burp Suite**. Я заповнила поля форми випадковими даними, увімкнула режим **Intercept** у **Burp Suite** та натиснула Submit, щоб перехопити сформований POST-запит перед його відправкою на сервер.

### Висновок
Вразливість виникла через некоректну реалізацію циклу перевірки на бекенді. Сервер шукає конкретні параметри `(secQuestion0, secQuestion1)`. Коли він їх не знаходить (бо ми змінили їхні імена), цикл звірки хешів відповідей просто не запускається. Оскільки в коді відсутнє правило "Default Deny" (яке б відхиляло запит, якщо перевірка не була успішно пройдена від початку до кінця), система діє за принципом "fail-open" і автоматично надає доступ. Натиснувши **Forward** у **Burp Suite**, я отримала змогу змінити пароль та успішно завершити завдання.
